# แผนงาน POS ร้านอาหารและร้านกาแฟ (F&B) บนแพลตฟอร์มเดิม

ร่างแผนวันที่ 15 ก.ย. 2569 — สำหรับตัดสินใจก่อนลงมือ ยังไม่ใช่สเปกละเอียด

## 0. ข้อเสนอหลัก: ไม่สร้างระบบใหม่ แต่เพิ่ม "ประเภทร้าน" ให้แพลตฟอร์มเดิม

POS ร้านค้าที่ใช้อยู่ (Go + PostgreSQL + Next.js, multi-tenant ด้วย RLS) มีของที่ร้านอาหารต้องใช้เหมือนกันอยู่แล้วราว 60%
สร้างใหม่แยกโปรเจกต์จะได้ระบบสองชุดที่ต้องดูแลคู่กันไปตลอด ข้อเสนอคือ

- เพิ่ม `stores.kind = retail | fnb` — ร้าน F&B ร้านเดียว**เปิดได้ทั้งสองแบบพร้อมกัน**: หน้าเคาน์เตอร์ (กาแฟ/สั่งกลับบ้าน ออกเลขคิว) และโต๊ะ (นั่งกิน สั่งหลายรอบ) เปิด/ปิดแต่ละแบบได้ที่ตั้งค่า ออร์เดอร์ทุกใบมี `channel = counter | dine_in | takeaway | delivery | self_order`
- หน้าจอฝั่งขายแยกตาม `kind` แต่ **หลังบ้านใช้ร่วมกันทั้งหมด** — ผู้ใช้/สิทธิ์ สมาชิก ลูกหนี้ กะ ลิ้นชัก เครื่องพิมพ์ พร้อมเพย์ สลิป รายงาน สำรองข้อมูล ปันผล (ร้านกาแฟสหกรณ์มีปันผลเหมือนกัน)
- เจ้าของหลายร้านต่างประเภทเข้าด้วยบัญชีเดียว สลับร้านที่หน้า login เหมือนเดิม และมี **หน้ารวมทุกสาขา (HQ)** ที่ไม่มีในตอนนี้

| ใช้ได้ทันทีโดยไม่แก้ | ต้องปรับ | ต้องสร้างใหม่ |
|---|---|---|
| ผู้ใช้ สิทธิ์ ร้าน RLS · สมาชิก/สะสมยอด · ลูกหนี้ · กะ/ลิ้นชัก (รวมพอร์ต COM) · พิมพ์ใบเสร็จ/สลิป/รายงาน · พร้อมเพย์ QR + ถ่ายสลิป · วิธีชำระ 8 แบบ · ปัดเศษ · สำรอง/กู้ข้อมูล · ปันผล · หน่วยนับ/แปลงหน่วย · AI ถาม-ตอบ (nl2sql) · LINE LIFF (mock) | `sales` ให้ผูกกับ order ได้ (บิลหนึ่งมาจากออร์เดอร์ที่แยกจ่าย) · บทบาทเพิ่ม พนักงานเสิร์ฟ/ครัว · โปรโมชันช่วงเวลา (happy hour) · ตั้งค่า service charge / VAT | เมนู+ตัวเลือก (modifier) · ออร์เดอร์และสถานะรายจาน · ผังโต๊ะ/โซน · จอครัว (KDS) + เครื่องพิมพ์ครัวตามสถานี · แยก/รวม/ย้ายบิล · สั่งเองผ่าน QR ที่โต๊ะ · คิว/เรียกรับ · สูตรอาหาร → ตัดสต็อกวัตถุดิบ · จอง/รอคิว · ระบบเรียลไทม์ |

## 1. ผู้ใช้และหน้าจอหลัก (แยกตามคนที่ถือเครื่อง)

### ร้านกาแฟ / counter service (สั่งที่เคาน์เตอร์ จ่ายก่อน รับที่บาร์)
| ใคร | หน้าจอ | สิ่งที่ต้องเร็ว |
|---|---|---|
| แคชเชียร์ | **Quick Order** — กริดเมนูรูปใหญ่ กดแล้วเด้งตัวเลือก (ขนาด/หวาน/น้ำแข็ง/นม/ท็อปปิ้ง) แล้วจ่าย | สั่ง 1 แก้ว ≤ 4 ครั้งกด · เลือกตัวเลือกด้วยนิ้วบนแท็บเล็ต |
| บาร์ | **KDS** — การ์ดออร์เดอร์เรียงตามเวลา แตะ = เริ่มทำ, แตะ = เสร็จ | ไม่ต้องใช้เมาส์ · เสียงเตือนออร์เดอร์ใหม่ |
| ลูกค้า | **จอเรียกคิว** (จอ TV/แท็บเล็ตหันออก) เลขคิว "กำลังทำ / รับได้" + สั่งล่วงหน้าผ่าน LINE มารับ | |

### ร้านอาหาร / table service (นั่งโต๊ะ สั่งหลายรอบ จ่ายทีหลัง)
| ใคร | หน้าจอ | สิ่งที่ต้องเร็ว |
|---|---|---|
| พนักงานเสิร์ฟ (มือถือ/แท็บเล็ต) | **ผังโต๊ะ** สีตามสถานะ → แตะโต๊ะ → **สั่งอาหาร** ระบุที่นั่ง/คอร์ส/หมายเหตุ → **ส่งครัว** | เดินไปโต๊ะแล้วสั่งได้เลย ไม่ต้องกลับเคาน์เตอร์ |
| ครัวแต่ละสถานี | **KDS** เฉพาะจานของสถานีตัวเอง (ครัวร้อน / บาร์ / ของหวาน) + เครื่องพิมพ์ครัวสำรอง | เห็นเวลารอ · จานที่นาน > N นาทีขึ้นแดง |
| แคชเชียร์ | **เช็คบิล** จากโต๊ะ → แยกบิลตามที่นั่ง/รายการ/หารเท่า → จ่ายหลายวิธี → ใบเสร็จ | |
| ลูกค้า | **สแกน QR ที่โต๊ะ** → เมนูบนมือถือ → สั่งเอง → ดูสถานะจาน → จ่ายพร้อมเพย์ที่โต๊ะ | ไม่ต้องลงแอป · ใช้ผ่านเบราว์เซอร์/LINE |

### เจ้าของ / HQ
- **แดชบอร์ดรวมทุกสาขา** เลือกช่วงเวลา เทียบสาขา · ยอดขายต่อชั่วโมง · เมนูขายดี/ขายไม่ออก (menu engineering: ดาว/ม้างาน/ปริศนา/หมา) · เวลาเฉลี่ยตั้งแต่สั่งจนเสิร์ฟ · ยอดต่อหัว · ต้นทุนวัตถุดิบต่อจาน
- **เมนูกลาง** ตั้งครั้งเดียวใช้ทุกสาขา แต่ละสาขาปิดเมนู/ตั้งราคาต่างได้
- ทุกอย่างที่มีอยู่แล้ว: ลูกหนี้ สมาชิก กะ รายงาน สำรองข้อมูล ปันผล

## 2. ฟีเจอร์ที่ทำให้ "ทันสมัยที่สุด" จริง ไม่ใช่แค่สวย

| ฟีเจอร์ | ทำไมสำคัญ | มีฐานอยู่แล้ว |
|---|---|---|
| **เรียลไทม์ทั้งร้าน** — เสิร์ฟกดส่งครัว จอครัวขึ้นทันที ครัวกดเสร็จ จอเสิร์ฟ/ลูกค้าเปลี่ยนทันที | หัวใจของ POS ร้านอาหาร ถ้าช้าคนจะกลับไปตะโกน | proxy SSE ของ AI (`compress:false`) ใช้ทางเดียวกัน |
| **QR สั่งเองที่โต๊ะ** + จ่ายพร้อมเพย์ที่โต๊ะ | ลดคนเสิร์ฟ ลดสั่งผิด ลูกค้าไม่ต้องรอเรียก | LIFF + PromptPay payload + สลิป |
| **KDS แทนกระดาษ** แต่มีเครื่องพิมพ์ครัวเป็นทางสำรองเมื่อเน็ตล่ม | ครัวไทยยังชอบกระดาษ ให้เลือกได้ต่อสถานี | RAW printing ที่เพิ่งทำเรื่องลิ้นชัก |
| **ทำงานต่อได้ตอนเน็ตล่ม (offline-first)** สั่ง/พิมพ์ครัว/รับเงินสดได้ แล้ว sync เมื่อกลับมา | ร้านต่างจังหวัดเน็ตสะดุดจริง | ต้องสร้าง: PWA + คิวออร์เดอร์ใน IndexedDB |
| **สูตรอาหาร → ตัดสต็อกวัตถุดิบอัตโนมัติ** + บันทึกของเสีย | รู้ต้นทุนจริงต่อจาน รู้ว่านมจะหมดวันไหน | สินค้า/หน่วยนับ/แปลงหน่วย/ความเคลื่อนไหวสต็อก |
| **โปรโมชันตามเวลา/วัน** happy hour, ซื้อ 2 แถม 1, คอมโบ | | promotions มีอยู่ ต้องเพิ่มเงื่อนไขเวลา |
| **LINE**: สั่งล่วงหน้า แจ้งเตือนอาหารเสร็จ สะสมแต้ม/แสตมป์ ใบเสร็จอิเล็กทรอนิกส์ | ลูกค้าไทยอยู่ใน LINE | LIFF mock พร้อมต่อของจริงเมื่อมี channel |
| **AI** (T-LLM): ถามยอดด้วยภาษาพูด, พยากรณ์ยอดขายรายชั่วโมงเพื่อจัดคน/เตรียมของ, แนะนำเมนูที่ควรเลิกขาย | | nl2sql + gateway มีแล้ว |
| **บริการเดลิเวอรี** รับออร์เดอร์จาก LINE MAN / Grab เข้าจอครัวจอเดียว | ถ้าร้านใช้ | ยังไม่มี · ต้องรอ API ของแต่ละเจ้า (ทำเฟสท้าย) |

## 3. รูปลักษณ์: "3D" ที่ใช้งานได้จริงบนแท็บเล็ตราคาถูก

ข้อเสนอคือ **3D ตรงที่ 3D ช่วยให้เข้าใจง่ายขึ้น และแบน-เร็วตรงที่ต้องกดเร็ว**

- **ผังโต๊ะแบบ isometric 3D** (react-three-fiber) — ตัวชูโรงของระบบ โต๊ะเป็นก้อนสามมิติ เห็นโซน ผนัง ระเบียง สีตามสถานะ (ว่าง/นั่ง/รออาหาร/เช็คบิล) มีจังหวะเต้นเมื่อมีจานรอนาน แตะโต๊ะแล้วกล้องเลื่อนเข้าหาแล้วเปิดแผงออร์เดอร์ · มี **ตัวแก้ผัง** ลากวางโต๊ะ หมุน ตั้งจำนวนที่นั่ง
- **หน้าสั่งอาหาร / KDS / เช็คบิล เป็นกลาส 2D ที่มีความลึก** (เงาหลายชั้น การ์ดยกตัวเมื่อแตะ เปลี่ยนหน้าแบบลื่นด้วย framer-motion) — ไม่ใส่ WebGL ในหน้าที่ต้องกดวินาทีละหลายครั้ง เพราะแบตและความร้อนของแท็บเล็ต
- **จอเรียกคิว / จอลูกค้า** ทำเต็มที่ได้ เพราะไม่ต้องรอการกด — เลขคิวลอย 3D พื้นหลังเคลื่อนไหว โลโก้ร้าน
- **กติกาประสิทธิภาพ**: ลื่น 60 fps บนแท็บเล็ต Android ราคา 5–7 พันบาท · ถ้าอุปกรณ์ไม่มี WebGL หรือเฟรมตก ผังโต๊ะสลับเป็น 2D SVG อัตโนมัติ · หน้าครัวต้องอ่านออกจากระยะ 2 เมตร ตัวอักษรใหญ่ คอนทราสต์สูง มีโหมดมืดสำหรับบาร์
- ใช้ธีมกลาสเดิมเป็นฐาน แต่ทำ **ชุดสีต่อร้าน** (โลโก้ สีหลัก) เพราะร้านกาแฟอยากได้หน้าตาเป็นของตัวเองมากกว่าร้านสหกรณ์

## 4. โมเดลข้อมูลที่เพิ่ม (ทุกตารางมี `store_id` + RLS เหมือนเดิม)

```
menu_categories, menu_items (ผูก products เพื่อสูตร/สต็อก, รูป, ราคาต่อสาขา, สถานี)
modifier_groups (ขนาด/หวาน/นม…, บังคับเลือก?, เลือกได้กี่อัน), modifiers (ราคาบวก)
combos, combo_items
floor_plans, zones, tables (ชื่อ ที่นั่ง x y หมุน รูปทรง), table_sessions (เปิด/ปิดโต๊ะ จำนวนคน)
orders (โต๊ะ/กลับบ้าน/เดลิเวอรี/สั่งเอง, service charge, สถานะ)
order_items (จาน ตัวเลือก จำนวน ที่นั่ง คอร์ส หมายเหตุ สถานี
             สถานะ: รอส่ง → ส่งครัว → กำลังทำ → เสร็จ → เสิร์ฟ → ยกเลิก)
order_events (ใครกดอะไรเมื่อไร — ใช้คำนวณเวลาครัวและตรวจย้อนหลัง)
kitchen_stations (ครัวร้อน/บาร์/ของหวาน → KDS และ/หรือเครื่องพิมพ์)
recipes, recipe_lines (เมนู → วัตถุดิบ+หน่วย), waste_logs
self_order_sessions (โทเค็น QR ต่อโต๊ะ หมดอายุเมื่อปิดโต๊ะ)
queue_tickets (ร้านกาแฟ: เลขคิว สถานะ)
reservations, waitlist
sales.order_id (บิลจากออร์เดอร์ — ออร์เดอร์เดียวแยกได้หลายบิล)
```

ของเดิมที่ไม่ต้องแตะ: `sales/sale_lines/sale_payments` (ใบเสร็จ รายงาน ปันผล ยังทำงานเหมือนเดิม), `members`, `ar_*`, `shifts`, `stock_movements`

## 5. สถาปัตยกรรมส่วนที่ต่างจากร้านค้า

- **Event hub ต่อร้าน** ใน Go: ทุกการเปลี่ยนสถานะออร์เดอร์เขียน `order_events` แล้ว broadcast ผ่าน **SSE** `/api/v1/stream?store=…&channel=kitchen|floor|table:<id>` — เลือก SSE ก่อน WebSocket เพราะผ่าน Next proxy ที่มีอยู่ได้เลย ไม่ต้องเปิดพอร์ตเพิ่ม และเรากดจากฝั่ง client อยู่แล้ว (WebSocket ค่อยเพิ่มถ้าต้องการสองทาง)
- **Offline**: หน้าสั่งอาหารเป็น PWA เก็บเมนูและออร์เดอร์ค้างใน IndexedDB, เครื่องพิมพ์ครัวต่อ LAN สั่งพิมพ์ตรงจากเบราว์เซอร์ผ่าน RAW ไม่ต้องผ่านเซิร์ฟเวอร์ → ตอนเน็ตล่มยังสั่ง/พิมพ์/รับเงินสดได้, sync กลับเมื่อเน็ตมา ด้วย idempotency key ต่อออร์เดอร์
- **สั่งเองที่โต๊ะ**: หน้า `/t/<token>` ไม่ต้อง login, สิทธิ์จำกัดแค่ session โต๊ะนั้น, rate-limit, ลูกค้าเห็นเฉพาะออร์เดอร์ตัวเอง
- **ฮาร์ดแวร์**: เครื่องพิมพ์ครัว LAN (ESC/POS) · KDS = แท็บเล็ต/จอสัมผัสเปิดเบราว์เซอร์ · เครื่องพิมพ์ใบเสร็จ/ลิ้นชัก/พร้อมเพย์ ใช้ของเดิมทั้งหมด · จอเรียกคิว = TV ต่อ Chromecast/กล่อง Android เปิดหน้าเว็บ

## 6. เฟสงานและสิ่งที่ "โชว์ได้" ในแต่ละเฟส

| เฟส | เวลา | ส่งมอบ | โชว์อะไรได้ |
|---|---|---|---|
| **0 ฐาน** | 2 สัปดาห์ | `stores.kind`, บทบาทใหม่, เมนู+modifier+คอมโบ, ออร์เดอร์และสถานะ, event hub SSE, ธีมต่อร้าน | เมนูขึ้นจอ สั่งได้ สถานะวิ่งข้ามจอ |
| **1 ร้านกาแฟ MVP** | 3 สัปดาห์ | Quick Order, ตัวเลือกเครื่องดื่ม, จ่ายทุกวิธี+พร้อมเพย์, ใบเสร็จ, KDS บาร์, จอเรียกคิว, กะ/ลิ้นชัก | **ร้านกาแฟเปิดใช้จริงได้** |

## 7. ความเสี่ยงและเรื่องที่ต้องตัดสินใจก่อนเริ่ม

1. **ร้านแรกที่จะใช้คือร้านแบบไหน** — กาแฟ (counter) หรืออาหาร (โต๊ะ)? ตัดสินลำดับเฟส 1/2
2. **ครัวใช้จอหรือกระดาษ** — ถ้าครัวไม่ยอมใช้จอ เฟส 1 ต้องมีเครื่องพิมพ์ครัว LAN ตั้งแต่แรก (ต้องซื้อเพิ่ม ~3–5 พันบาท/สถานี)
3. **อุปกรณ์เสิร์ฟ** — มือถือพนักงานเอง หรือแท็บเล็ตของร้าน? กระทบขนาดหน้าจอที่ออกแบบและเรื่อง offline
4. **VAT** — ร้านจดทะเบียน VAT ไหม (ใบกำกับภาษี, ราคารวม/แยก VAT, service charge คิด VAT)
5. **LINE Official Account** ของจริง — ต้องมีก่อนเฟส 3 ถึงจะทดสอบกับลูกค้าจริงได้ (ตอนนี้ mock)
6. **3D บนเครื่องเก่า** — ต้องตั้งเป้าอุปกรณ์ขั้นต่ำให้ชัด และมีทาง 2D fallback เสมอ (ใส่ไว้ในแผนแล้ว)
7. **เดลิเวอรี** — API ของ LINE MAN/Grab ต้องสมัครเป็นพาร์ตเนอร์ ใช้เวลาและไม่ขึ้นกับเรา จึงวางไว้ท้ายสุด
8. **โค้ดเดิม** — ตาราง `sales` ต้องรับ `order_id` และหน้าจอ POS ร้านค้าต้องไม่กระทบ ทำด้วย feature flag ตาม `stores.kind` และ e2e ชุดเดิมต้องผ่าน 100% ทุกเฟส

## 9. สูตรอาหารและการตัดสต็อกวัตถุดิบ (ทำในเฟส 0)

**หลักการ**: เมนูหนึ่งรายการมีสูตรได้หนึ่งสูตร สูตรบอกว่าทำ "1 หน่วยขาย" (1 จาน / 1 แก้ว) ใช้วัตถุดิบอะไรเท่าไร ตัวเลือก (modifier) เพิ่ม/แทนวัตถุดิบได้ เมื่อครัว**เริ่มทำ**จานนั้น ระบบตัดวัตถุดิบตามสัดส่วน × จำนวนที่สั่ง ลง `stock_movements` ชนิด `recipe` โดยอ้างถึงรายการในออร์เดอร์ จึงตรวจย้อนได้ทุกจานว่าตัดอะไรไปเมื่อไร

```
recipes        เมนู → yield_qty (สูตรนี้ได้กี่หน่วยขาย ปกติ 1; น้ำซุปหม้อละ 10 ชาม = 10)
recipe_lines   วัตถุดิบ (products) · qty · unit · factor_to_stock (แปลงเป็นหน่วยที่นับสต็อก เช่น 200 มล. ของนมที่นับเป็นลิตร = 0.001)
               · waste_pct (เผื่อเสีย) · ผูกกับ เมนู หรือ modifier ก็ได้
               modifier มี mode: add (เพิ่ม เช่น ช็อตเสริม +18 g) / replace (แทน เช่น นมโอ๊ตแทนนมสด)
```

**ตัดเมื่อไร** ตั้งค่าได้ต่อร้าน: `on_send` (ส่งครัว = "ทำอาหารแล้ว" — ค่าเริ่มต้นตามที่ร้านบอก) / `on_ready` (ครัวกดเสร็จ) / `on_pay` (ตอนจ่าย)
**ยกเลิกหลังตัดแล้ว** ถามว่า "ทำไปแล้วหรือยัง" → ทำแล้ว = บันทึกเป็นของเสีย (`waste`) / ยังไม่ทำ = คืนสต็อก (`recipe` กลับด้าน)

**สูตรคำนวณ** ต่อวัตถุดิบหนึ่งตัว
`ตัด = qty × factor_to_stock × (1 + waste_pct) × จำนวนที่สั่ง ÷ yield_qty` ปัดเป็น 3 ตำแหน่ง (หน่วยนับของระบบ)
ต้นทุนจาน = Σ(ตัด × ต้นทุนเฉลี่ยของวัตถุดิบ) บันทึกลง `sale_lines.cost_avg` → รายงานกำไรขั้นต้นเดิมใช้ได้ทันที

**วัตถุดิบกึ่งสำเร็จ** (น้ำซุป ซอส น้ำเชื่อม ที่ทำเป็นหม้อ): เป็นสินค้าที่มีสูตรของตัวเอง กด "ผลิต" 1 หม้อ → ตัดวัตถุดิบต้นทาง เพิ่มสต็อกของกึ่งสำเร็จ (`production`) แล้วจานที่ใช้มันตัดจากสต็อกกึ่งสำเร็จอีกที — ทำในเฟส 1

**รายงานที่ตามมา**: วัตถุดิบใกล้หมด (ใช้ low-stock เดิม) · วัตถุดิบที่ใช้ต่อวัน · ต้นทุนจริงต่อจาน vs ราคาขาย · ของเสีย
